# Research: App Foundation and Shell

All Technical Context items are resolved. Decisions below were checked against the Next.js docs
shipped in `node_modules/next/dist/docs/` (this version has breaking changes, see `AGENTS.md`).

## 1. Route params under Cache Components

- **Decision**: `next.config.ts` already sets `cacheComponents: true`. Use `generateStaticParams`
  on `learn/[language]` returning every language slug from the data, so language pages prerender at
  build time. Do not `await params` at the top level of a layout; the language layout passes the
  `params` promise to a small child that awaits it.
- **Rationale**: The docs say that without `generateStaticParams` params are runtime data and need
  Suspense, and that awaiting params in a layout stops it prerendering. Slugs are known at build
  time, so full static output is available.
- **Alternatives considered**: Leave params dynamic and wrap in Suspense (worse: no static HTML,
  needless loading states for known slugs). Turn `cacheComponents` off (rejected: it is a project
  setting made by the scaffold, not ours to change here).

## 2. Unknown and coming-soon slugs

- **Decision**: Use `dynamicParams = false` on the `[language]` segment so slugs outside the data
  fall through to the not-found page, and `notFound()` as a belt-and-braces check in the layout.
  Coming-soon languages are in `generateStaticParams` too, and the layout renders a "coming soon"
  notice in place of the page.
- **Rationale**: Spec FR-012 and FR-024: friendly not-found for unknown slugs, friendly notice for
  coming-soon ones. Static params keep both cheap.
- **Not-found page**: `src/app/not-found.tsx` sits outside the `(shell)` route group, so it does
  not get the shell layout automatically. Both it and `(shell)/layout.tsx` render a shared
  `ShellFrame` component (skip link, header, `<main id="main">`, footer) so the header and footer
  live in one place. Slugs are lowercase only; other cases are unknown slugs and show not-found.
  The `/nope` check in the quickstart confirms unmatched URLs reach this page; if the docs'
  `global-not-found` convention turns out to be required for them, use it with `ShellFrame` too.
- **Alternatives considered**: Exclude coming-soon slugs from static params (they would then 404,
  contradicting the clarified "friendly coming soon" behaviour).

## 3. Design tokens in Tailwind v4

- **Decision**: Replace the scaffold `globals.css` theme with `@theme` variables generated by hand
  from `docs/design-tokens.json`: colours (`cream`, `paper`, `ink`, `slate`, `coral`, `coral-text`,
  `coral-tint`, `teal`, `teal-text`, `sun`, `hairline`), font families, spacing aliases
  (`space-1`…`space-16`), radii (`radius-sm|md|lg|pill`), shadows (`shadow-sm|md`), and text styles
  (`display`, `title`, `heading`, `body-lg`, `body`, `label`, `caption`, `translit`, `arabic-ui`,
  `transcript`). Remove the scaffold's dark-mode media query: the design system is light only.
  Leave the existing `@tailwindcss/turbopack` rule in `next.config.ts` untouched.
- **Rationale**: Constitution VI requires building from tokens via Tailwind. v4 is configured in
  CSS, so no `tailwind.config` file is needed. Tailwind's default spacing is already a 4px base,
  so only the named aliases are added.
- **Alternatives considered**: A generator script from the JSON (extra moving part for about 40
  values; revisit if tokens change often). Keeping the scaffold's dark mode (contradicts the design
  system).

## 4. Fonts

- **Decision**: Load Nunito (weights 700, 800), Inter, IBM Plex Sans Arabic (arabic subset,
  weights 500, 600) and Noto Naskh Arabic (arabic subset, weight 400) with `next/font/google`, each
  exposing a CSS variable consumed by the `@theme` family tokens. Fallback stacks come from the
  design tokens. Use `display: "swap"`.
- **Rationale**: Docs say `next/font` self-hosts fonts and avoids layout shift, and covers
  FR-019. Family names in the tokens match.
- **Alternatives considered**: A `<link>` to Google Fonts (extra network origin, layout shift).

## 5. Language data and build-time validation

- **Decision**: `content/languages.json` is parsed by a `zod` schema in `src/lib/languages.ts` at
  module load. The module is imported by the static `generateStaticParams`, the layout and the
  header, so an invalid file fails `next build` with a message naming the entry and field. Schema
  rules: required fields, slug pattern `^[a-z0-9]+(-[a-z0-9]+)*$`, unique slugs and codes,
  `direction` is `"rtl"` or `"ltr"`, `status` is `"available"` or `"coming-soon"`, at least one
  available language. Unit tests cover each failure.
- **Rationale**: Constitution VIII and FR-022. `zod` is already in `node_modules` as a transitive
  dependency, but it must become a direct dependency to be relied on. It is small, typed, and also
  useful for the later content schemas (videos, hosts), so one validation approach is used
  throughout. Constitution VII asks for a reason for each new dependency: this is it.
- **Alternatives considered**: Hand-written validation (more code to test and maintain). A separate
  prebuild script (a second place validation can drift from runtime types).

## 6. Target-language text

- **Decision**: A server-safe `TargetText` component takes `language` (a validated `Language`) and
  `children`, and renders an element with `dir`, `lang` and a font and size class chosen by the
  language's `script` and `fonts` data. For Arabic: `arabic-ui` style for UI text, with a
  `variant="transcript"` option using the Naskh `transcript` token (26px/48px). Direction comes
  only from data. `unicode-bidi: isolate` keeps the block from disturbing surrounding English.
- **Rationale**: Constitution IV and V, FR-025 to FR-028. Using one component stops later screens
  setting `dir` and `lang` by hand. It never transforms the text, so tashkeel is shown as stored.
- **Alternatives considered**: A CSS-only `[lang=arz]` rule (would not set `dir` and `lang`
  attributes, which assistive technology needs).

## 7. Header variants for Landing and Done

- **Decision**: Every placeholder page uses the standard header and footer. The landing and done
  designs use different header layouts, so those variants are left to the specs that build those
  screens; the shell exposes a `variant` prop only if that spec needs it.
- **Rationale**: FR-007 only requires them to remain in the shell system, and the placeholders
  have no content to make the difference visible. Avoids speculative props.
- **Alternatives considered**: Building all three variants now (YAGNI; untestable without content).

## 8. Navigation and the current-page marker

- **Decision**: `MainNav` is the only client component in the shell. It uses `usePathname()` to set
  `aria-current="page"` and the coral-tint pill from the design. It is rendered inside `<Suspense>`
  with a non-marked nav as fallback so the rest of the header stays in the static shell. Nav
  hrefs point at the default language (the first available language in the data) when the visitor
  is not inside a language path, and at the current language when inside one.
- **Rationale**: Docs require Suspense around runtime-dependent APIs under Cache Components.
  Keeping the marker client-only follows Constitution VII (client components only for interactivity).
- **Alternatives considered**: Marking the current page in each page component (duplicated, easy
  to forget).

## 9. Route shape

- **Decision**: See [contracts/routes.md](contracts/routes.md). Language-independent: `/`,
  `/onboarding`, `/pricing`. Language-scoped: `/learn/[language]` (library), `/learn/[language]/watch`
  (player), `/learn/[language]/done`, `/learn/[language]/roadmap`, `/learn/[language]/hosts`.
  The player route is `/watch` without a video segment because videos do not exist yet; the content
  spec will add `/watch/[video]` and `/hosts/[host]`.
- **Rationale**: Matches product.md URL rule and the clarified Hosts route, and adds nothing beyond
  the eight MVP screens.
- **Alternatives considered**: A sample video slug now (invents content that is out of scope).

## 10. Testing setup

- **Decision**: Add `vitest`, `@vitejs/plugin-react`, `jsdom`, `@testing-library/react`,
  `@testing-library/dom` and `vite-tsconfig-paths` as dev dependencies, with `vitest.config.mts`
  following the Next.js Vitest guide, and `npm test` and `npm run typecheck` scripts. Tests live in
  `tests/unit/`.
- **Rationale**: Constitution IX needs tests for core logic. The Next.js guide recommends Vitest
  and RTL for synchronous components and E2E for async ones. A full E2E suite is not worth
  adding for placeholder pages; the build and the quickstart walkthrough cover routing.
- **Alternatives considered**: Jest (more config for TypeScript and ESM). Playwright now (heavy for
  empty pages; reconsider with the first interactive screen).

## 11. Accessibility checks

- **Decision**: Skip link as the first focusable element, landmarks `header`, `nav` (labelled
  "Main"), `main` and `footer`, one `h1` per page via `PlaceholderPage`, `:focus-visible` ring using
  `ink`, minimum 44px hit areas on nav links, the Hours pill and the account button, and
  `prefers-reduced-motion` respected by limiting transitions to colour changes. Contrast values
  come from the token table, which already lists ratios; the quickstart includes a manual
  keyboard walkthrough and an automated axe run in the browser.
- **Alternatives considered**: Adding `jest-axe` to unit tests (limited value on static
  placeholder markup).
